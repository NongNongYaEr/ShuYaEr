# 发布与授权资料（草案配套）

适用草案：draft-2026-10-24.2。以下是准备资料与实际处理流程，不是已授予的许可，不表示网站已经实现同意留痕或完整授权凭证。

## 发布前填写的信息

| 项目 | 要填写或核实的内容 |
| --- | --- |
| 权利人与运营者 | 真实自然人姓名或登记主体名称；若二者不同，写清授权关系。对外公开必要信息，不将身份证号码放入公开仓库 |
| 联系方式 | 用户未登录时也能使用的授权与售后渠道；站内反馈可作补充 |
| 软件范围 | 软件名称、版本／标签、适用文件、构建与发行包、依赖及第三方声明 |
| 素材范围 | 素材 ID、名称、作者、版本、包内清单、权利来源与是否有特殊许可 |
| 合同要素 | 授权地域、许可期限、使用者身份、可授予的权利、限制、约定费用和争议处理方式 |
| 仍需决定 | 团队成员与客户的可编辑文件交付、分包、署名、原版镜像／独立插件／托管服务，以及退款后的具体授权处理 |

已决定：有效会员期间合法领取的素材版本，正常到期后仍可用于新旧商业项目；到期停止按该权益继续领取。不将新版本更新或重新发链接混为既有授权。

## 软件随包提示模板

> 草案模板，填齐并采用正式协议后才能发布：
>
> 软件：〔名称〕〔版本〕；权利人：〔真实姓名／主体〕。
> 本软件免费使用；源码按〔协议名称、版本、可访问全文地址〕公开，不属于 OSI 开源许可。未经另行书面授权不得发行或销售修改版。第三方组件适用各自许可证。
> 配套素材独立授权。授权申请与问题反馈：〔可用渠道〕。

提示用于引导阅读全文，不能只靠这一段使高额违约金自动生效。对应正式协议与第三方声明应随软件文件一并保留。

## 每份素材随包提示模板

> 草案模板，填齐并采用正式协议后才能发布：
>
> 素材：〔ID／名称／版本〕；作者与权利人：〔信息〕；内容清单：〔清单或随包文件〕。
> 适用〔协议名称、版本、全文地址〕。允许用于商业作品，未经单独授权不得转售素材原文件或修改版素材。
> 有效会员期间合法领取的本版本，正常到期后仍可用于新旧商业项目；未来更新、未领取素材与到期重新发放链接不自动包含。
> 特殊授权或第三方内容：〔如有则明确列出〕。授权与争议联系：〔渠道〕。

随包提示不能单独证明某个账号已取得授权；也不宜把所有素材使用者的身份或购买记录放进公共包。

## 单独书面授权需要明确什么

使用者通过正式联系渠道提交：申请者、软件或素材及版本、拟修改内容或用途、计划渠道、是否收费、授权地域与期限。回复或协议须明确授权人身份、被许可人、准许的行为及限制，必要时另定费用与责任。

申请登记、自动回执、客服“已收到”都不等于许可。普通售后答疑不能被误解为转售或修改版发行的特别授权。

## 怎样让正式许可可核对

1. 固定协议版本和全文，保留旧版本；软件与素材页、结算及领取前提供适用全文。对转售限制、高额责任等重大条款作合理提示并能解释，不能靠预先勾选或静默同意。
2. 仅在用户实际确认后记录必要信息：账号、协议类型与版本、文本摘要、服务器时间、适用资源／文件版本及关联订单（如有）。付款、领取、同意是不同事实，分别记录；请求去重与版本匹配须在服务端校验。
3. 向用户提供可保存的适用文本与领取明细。未来更新、正常到期、退款、撤回发布和历史版本变化不能静默改写已经发生的记录。
4. 记录应有适当访问控制和备份；保存用途、期限及个人信息处理安排应与隐私政策一致。不为“证据”无限收集身份证号、设备指纹等无关数据，也不补造历史同意。

上述仅为待实施方案。目前网站仍是草案说明与原有领取记录，未接入正式协议确认。

## 发生疑似侵权时怎样处理

先固定作品与权属证据、涉案版本、对方页面／交付内容和时间，再核对实际授权。保存合法获取的原始资料和来源，不仅保留裁切截图；必要时咨询律师采用适当的证据保全方式。

通知应写明权利人、涉及作品及版本、被指行为、证据位置、请求停止的具体行为、联系及提出异议的方式。给对方合理说明或纠正的机会；依法需要及时制止的，可另行申请司法救济。商业规模、违法所得、损失和合理维权开支应分别举证，不用一个领取次数代替损失。

公开 GitHub Issues 不适合提交账号、订单或个人身份资料。误判应更正，不以通知冒充法院判决，也不自行开出行政罚款。
